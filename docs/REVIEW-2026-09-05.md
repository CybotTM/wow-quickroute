# Routing, security and reliability review — 2026-09-05

Baseline: `6633f19` (`main`, QuickRoute 1.16.0). This review includes corrective changes and new destination features. It is not an in-game certification or a completed Codex Security scan; that scan's native tools were unavailable in this session.

## Verdict

**The baseline does not fulfil its unrestricted “fastest route to any destination” promise.** A large passing mock suite concealed impossible transport links, incorrect flight-master state interpretation, omitted hearthstones and quest buttons which did not use the route calculation. The accompanying changes address these faults and improve useful coverage. Full Mapzeroth parity and universal access-aware routing remain unproven, with specific blockers below.

“Fastest” means the minimum estimated cost in the modeled travel graph, subject to known methods and available state. It cannot mean a proven fastest navigable path over arbitrary terrain, inside every dungeon, through every phase and to every NPC. There is no terrain/navigation mesh in this addon; walk/fly costs approximate distances and travel speeds.

## Findings addressed

| Priority | Baseline defect and player impact | Correction and regression evidence |
|---|---|---|
| P1 | `ConnectViaContinentRouting` manufactured 240/300-second cross-continent travel without a portal, boat or other actual link. Disconnected same-continent zones also received invented travel times. | Remove fabricated edges and return no route for missing topology. Weighted zone search chooses elapsed time rather than the first fewest-hop path. `test_routing_integrity.lua`, pathfinding and adjacency tests. |
| P1 | Map clicks changed the map ID without projecting the normalized coordinates. A destination could move to a different location. | Shared `ResolveMapPosition` projects through Blizzard world coordinates; it keeps the original point when projection is unavailable. Map-click and native-waypoint adapters use the shared result. `test_map_click_integrity.lua`. |
| P1 | Flight states were interpreted backwards: current master (`0`) was excluded while unreachable (`2`) could count as discovered. Discovery of any master in a zone unlocked the modeled master. | Use discovery API when available, correct the enum fallback and match the modeled master location. `test_routing_integrity.lua`. |
| P1 | Parallel methods to the same destination replaced one another by iteration order; refreshing weights could change earlier returned route results. | Retain alternatives and choose the cheapest current edge while preserving result snapshots. Graph and routing regressions. |
| P1 | Collapsing a final walk into a teleport/portal hid the required walk from the landing point to the target. | Preserve the final walking instruction and its own destination. Updated route-feature regressions. |
| P1 | Quest tracker buttons ranked teleports by same zone/continent, independently of travel time and the next actionable route step. | Use the actual calculated quest route and offer its first teleport only when it is the next action. UI/security regressions. |
| P2 | A same-zone route could mark early actions complete simply because a later step ended on the current map. | Conservative progress highlighting keeps required same-zone actions visible. `test_ui.lua`. |
| P2 | Equipment button configuration lacked a combat guard. Reused equipment callbacks and secondary mouse clicks could trigger unintended actions. | Guard protected changes, clear recycled action handlers, reserve secondary clicks for navigation, and use Blizzard's secure combat visibility driver. `test_ui_security_regressions.lua`. |
| P2 | Malformed SavedVariables roots crashed initialization; NaN/infinite/out-of-range settings reached frames and cost calculations. | Recover invalid roots, validate enum settings, clamp supported ranges and replace nonfinite values. `test_review_settings.lua`. |
| P2 | Choosing an unreachable map point could leave a pending route to a previous target. | Clear the pending result and retain the explicitly requested target, so an unrelated tracked quest cannot replace it. `test_map_click_integrity.lua`. |

Additional dungeon reliability fixes make Journal rescans idempotent, restore the selected Journal tier, keep entrance coordinates paired with their source map, and expose verified static entrances even before the Journal supplies tier metadata. Quest fallbacks no longer choose a zone midpoint or an arbitrary entrance on a map containing multiple dungeons. Hearth landing nodes cannot alias a city node just because the inn and city names match. Cross-zone walks remain alternatives to cooldown-bound teleports.

The new tests reproduce these behaviors rather than treating the baseline's output as the correctness oracle. Some older assertions required the faulty behavior (fabricated connectivity and hidden final walks); those assertions were replaced with executable-route requirements.

## Added destination workflows

- **Currency vendors:** the addon records a merchant's accepted currencies and the player's interaction position when the merchant is visited. Observations are scoped to character GUID and faction, validated and bounded to 500 records. The currency picker and `/qr currency <ID or exact localized name>` compare travel time to known vendors. This is a learned catalogue; an empty catalogue cannot discover unvisited shops. Moving NPCs, changed stock and phasing remain possible, and the UI labels observations accordingly.
- **Quest search:** expand from watched quests to available quest-log destinations plus current-map quest givers and objectives exposed by Blizzard. Missing coordinates remain unavailable; no zone midpoint is advertised as a quest endpoint.
- **Multi-destination trips:** paste up to 20 `/way mapID x y` or `/way #mapID x y` lines, or import active TomTom points across maps. Percent coordinates are validated; input is never executed. Follow input order or select the fastest next reachable stop. Each new leg is calculated from the player's current position and cooldowns. This greedy option does not prove an optimal total tour. Mark each stop reached to continue; trips are session-local.
- **Hearthstone binding:** learn the actual bind position from the bind event and use it only for the same character and matching current inn. Bound-location hearth items/toys/spells can then participate in routing. Before an observed binding, the addon does not invent its coordinates. Garrison and housing destinations require their own verified resolution.
- **Discoverability:** route-toolbar buttons expose currency vendors and multi-destination trips. Existing portrait, route cards, pooled controls and Settings integration are retained. Added strings have English defaults and German translations.

## Remaining release blockers for the user's full requirement

1. **Unlock and phase state.** A portal in the static database is not proof the current character can use it. Add verified requirements and a phase model, including zone changes, Zidormi transitions and explicitly unknown state. Test a character before and after each unlock. Do not insert guessed quest IDs.
2. **Missing travel topology.** With fabricated links removed, the baseline no-teleport dungeon fixture exposes 13 of 203 entrance routes without a documented connection per faction: ten Draenor entrances and three entries on maps 2512/2509. Ashran is disconnected from the mainland in the recorded graph. Verified transports or newly discovered taxi links may enable these routes. The coverage test enumerates the known missing maps and rejects new gaps; it does not assert universal reachability.
3. **Complete destination data.** Blizzard only supplies some active/current-map quest coordinates. All quest givers/endpoints and all currency vendors across the entire world require an independently verified, maintained dataset. A learned merchant catalogue is useful but not that dataset.
4. **Variable destinations and shortcuts.** Verify garrison/housing, random wormholes, Mole Machine choices, pet-dungeon ports and other NPC shortcuts individually, including access rules and cast/loading costs.
5. **Movement estimates.** Flying currently depends on zone flyability, and walking/flying use nominal speeds rather than verified riding capability and measured character travel speeds. Async vendor/trip comparisons span frames; moving during a batch can change which destination is cheapest. The chosen leg is refreshed, but ranking is an estimate across that interval.
6. **In-client acceptance.** Test on actual 12.1 retail with Alliance/Horde, relevant classes, a fresh character, restricted/secret API states, combat transitions, TomTom installed/absent, phasing and multiple languages/UI scales. Mock frames do not execute secure templates, detect taint or render screenshots. Visual appeal and absence of taint cannot be certified from standalone tests.
7. **Global optimality.** Complete travel-time and topology data are required before claiming the fastest supported route. Total multi-stop optimization with cooldown reuse constraints is a separate routing problem; the implemented next-stop heuristic is explicitly labeled.

## Security boundary and evidence limits

The runtime is a WoW addon sandbox. The reviewed input surfaces are SavedVariables, TomTom waypoint tables, Blizzard API responses, pasted waypoint text and secure action construction. There is no addon-message receiver, general imported-code evaluator or arbitrary network client in the reviewed addon sources. No confirmed remote exploit was established in these surfaces. This is a scoped conclusion, not a clean bill of health for all dependencies, the game client or future releases.

The principal confirmed action-safety issues were protected-frame mutation and unintended activation through recycled callbacks/secondary clicks; these are reported above as runtime correctness/reliability issues. User labels stay display data. CI actions are pinned to commit hashes; release secrets are passed through environment variables. This pass did not publish a release or perform a separate exhaustive supply-chain scan.

## Validation

Baseline: **13,909 passing Lua assertions**. Final integration: **14,498 passing assertions in each of discovery and reverse file order**, **39 Python generator tests**, and **luacheck 1.2.0: zero warnings/errors**. Both Lua file orders are required because the suite shares a mock runtime and namespace.

Mock-runtime performance sample: graph build averaged approximately 17 ms over 20 rebuilds; warm route calculation approximately 0.74 ms over 200 queries (278 nodes / 6,222 edges). Comparing 500 merchant locations synchronously took approximately 207 ms, which motivated the per-frame currency search. These measurements are host/mock CPU timings, not live WoW frame-time guarantees.

Primary API evidence used during implementation:

- [Blizzard UI source version](https://raw.githubusercontent.com/Gethe/wow-ui-source/live/version.txt): `12.1.0.69587` at review time. The declared TOC interface `120100` matches 12.1.0; that alone does not certify runtime compatibility.
- [Map API declarations](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/MapDocumentation.lua): coordinate projection.
- [Taxi API declarations](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/TaxiMapDocumentation.lua): discovery and taxi states.
- [Merchant API declarations](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/MerchantFrameDocumentation.lua): currencies accepted by a merchant.
- Quest APIs and secure state driver were checked against the same live Blizzard UI source mirror. Active TomTom waypoint shape was also checked against the installed TomTom source, not just QuickRoute's mocks.
