# AGENTS.md — QuickRoute

> Last updated: 2026-11-10

World of Warcraft addon (Lua 5.1) for optimal travel routing using teleports, portals, spells, and items. Uses Dijkstra's algorithm. Namespace: `QR`.

## Architecture

### Load Order
Defined in `QuickRoute.toc`. Localization → Utils → Data → Core → Modules → QuickRoute.lua → Tests.

A module loaded before `QuickRoute.lua` must not call into the `QR` namespace at
file scope — `QR:RegisterCombatCallback` and friends do not exist yet. Register
from `Initialize()` instead. The test runner fails the run when a file does not
load, which is what catches this.

### Key Patterns

| Pattern | Implementation |
|---------|---------------|
| Global caching | All files cache `string.format`, `table.insert`, `math.*` as locals at file top |
| Logging | `QR:Debug()`, `QR:Error()`, `QR:Warn()`, `QR:Print()` — never raw `print()` |
| Colors | `QR.Colors.*` from `Utils/Colors.lua` — never hardcoded hex/RGB |
| Player info | `QR.PlayerInfo:GetFaction()`, `:GetClass()`, `:HasEngineering()` — cached |
| Combat safety | `QR:RegisterCombatCallback(enterCb, leaveCb)` — centralized |
| Secure buttons | `SecureActionButtonTemplate` on UIParent, positioned via throttled OnUpdate |
| Frame pooling | UI.lua and TeleportPanel.lua use frame pools to prevent memory leaks |
| Localization | `QR.L["KEY"]` with metatable fallback to English |
| Tooltips | `QR.AddTooltipBranding(GameTooltip)` before `Show()`, `GameTooltip_Hide()` on leave |
| Debounce | `C_Timer.NewTimer` with `:Cancel()`, stored on module table |

### MainFrame Architecture
Single unified window with portrait header and tab bar. `UI.lua` and `TeleportPanel.lua` implement `CreateContent(parentFrame)` instead of standalone windows. Show/Hide/Toggle delegate to `QR.MainFrame`. Use `QR.MainFrame.isShowing` and `QR.MainFrame.activeTab` — never `QR.UI.isShowing` or `QR.TeleportPanel.isShowing`.

## Testing

- **Runner**: `~/.local/bin/lua5.1 tests/run_tests.lua`
- **File order**: `QR_TEST_ORDER` is `discovery` (default) or `reverse`. The files share one mock and one addon namespace, so a test that borrows a global -- a frame method, a `QR.db` key -- must put it back, or it breaks whichever file happens to run next.
- **Mock**: `tests/mock_wow_api.lua` provides full WoW API simulation (frames, events, tooltips, spells, items, C_Map, C_Timer, etc.)
- **Text width**: the mock measures a string at 7 px per byte (`GetStringWidth`), so a 100 px column holds 14 characters. When width-aware code makes an exact-string assertion fail on an ordinary label, widen the column rather than relax the test: 100 px columns cut real item names in-game too (#52).
- **Loader**: `tests/addon_loader.lua` loads addon in .toc order
- **In-game**: `/qrtest graph` runs graph tests inside WoW
- **UX enforcement**: `test_ux_consistency.lua` verifies 10 UX patterns across all modules
- **Layout tests**: `MockWoW:ComputeFrameBounds()` resolves anchor chains to absolute positions
- **Content frame size**: MainFrame's content frames get their size from two anchors, and the mock's `GetWidth()` returns only what `SetSize`/`SetWidth` stored, so a content frame reads 0 wide. Assert on `QR.MainFrame.frame:GetWidth()`, or resolve the content frame with `ComputeFrameBounds()`
- **Map positions**: addon code reads a `UiMapPoint` position both as `.x`/`.y` and through `:GetXY()`. A mock position carries both, or the path that reads the other form sees nil

### Test Contract
Files: `tests/test_<module>.lua`, discovered by the runner. Each file receives
`(T, QR, MockWoW)` as varargs — `local T, QR, MockWoW = ...` on the first line.

Register a test with `T:run("Module: behaviour", function(t) ... end)` and assert
through the `t` handle: `t:assert`, `t:assertEqual`, `t:assertNotNil`, `t:assertNil`,
`t:assertTrue`, `t:assertFalse`, `t:assertGreaterThan`, `t:assertTableCount`.

Never use bare `assert()`. It raises instead of recording, which aborts the rest
of the file and takes every later test in it with it.

Every assertion carries a message that names the observed value, so a failure
reads as a fact rather than a boolean.

### PlayerInfo in Tests
After changing `MockWoW.config.playerFaction`, call `QR.PlayerInfo:InvalidateCache()`.

### Searches that span frames
`CalculatePathAsync` runs a search in a coroutine and continues it from
`C_Timer.After`. A stubbed `CalculatePath` that returns at once finishes inside
the call that asked for it, so a test of what happens *while* a search runs
(the window closed, another request made) passes on broken code. Stub it to
`coroutine.yield()` once, and replace `C_Timer.After` with a queue the test
drains itself. `tests/test_routingapi.lua` (`withDriver`) and
`tests/test_poirouting.lua` (`withQueuedSearch`) show the shape.

Code that calls `CalculatePath` directly, such as `MultiRoute:SelectNext`, needs
a stub that does not yield: the call sits inside `pcall`, which swallows the
yield error, so the path is skipped and an assertion about its effect holds for
nothing. Assert that the path was taken as well (for a trip, `currentIndex`).

### Map ids in tests
`C_Map` reports UI map ids. `C_EncounterJournal.GetInstanceForGameMap` takes a
game map id, the 8th value of `GetInstanceInfo`. A test that touches both uses
different numbers for them (`MockWoW.config.currentMapID` and
`MockWoW.config.instanceMapID`): with one number for both, passing the wrong id
cannot fail. Issue #98 was invisible to the suite for that reason.

### Reading simulator renders
The screenshots come from wow-ui-sim (`screenshots/seeds/README.md`). Two
artifacts in a render are simulator defects, not addon defects:

- A raw `tem:<id>:::` in an item name: the simulator's parser for a `|cn`
  named color escape consumes the `|Hi` of the item link that follows it
  (fix: [Osso/wow-ui-sim#10](https://github.com/Osso/wow-ui-sim/pull/10)).
- `Â·` where the source has `·`: the string went through `string.format`,
  which re-encodes the non-ASCII bytes of the format literal in wow-ui-sim
  builds older than 2026-10-27. Upstream `master` carries the fix since merge
  [62c00833e](https://github.com/Osso/wow-ui-sim/commit/62c00833e). Plain
  `SetText` renders it correctly.

## Code Style

- **Language**: Lua 5.1 (WoW runtime) — no `goto`, no bitwise ops, no `//` division
- **Indentation**: 4 spaces
- **Local caching**: First lines of every file cache globals as locals
- **Nil safety**: Always guard `C_Map and C_Map.FunctionName` before calling
- **Strings**: Double quotes preferred
- **Comments**: `-- Single line` and `--- Doc comment`

## Heuristics

| When | Do |
|------|----|
| Adding a teleport | Add to `TeleportItems.lua`, add `DEST_*` to all 10 locales in `Localization.lua`, add `DEST_L_KEYS` mapping in `TeleportPanel.lua` if needed |
| Adding a module | Add to `QuickRoute.toc` and `QuickRoute_Camelot.toc` in the correct section, create a test file. `tests/addon_loader.lua` reads the TOC, so no list to update there |
| Adding a portal seen in WoW Forever that its tables do not list | Add it to `scripts/data/forever_observed_portals.json` (one direction, the faction it was seen for, a `source` saying who saw it) and regenerate; never edit `Data/Forever/`. The generator adds it only while `scripts/data/forever_zone_survey.json` holds a loading-screen crossing in that direction with both ends within 50 yd, so import the survey first |
| Changing a retail data file | Regenerate `Data/Forever/` with `scripts/generate_forever_data.py` when the change should reach WoW Forever too; a new QR table needs a Forever definition, or `tests/test_flavor_tocs.lua` fails |
| Showing tooltip | `QR.AddTooltipBranding(GameTooltip)` before `Show()`, suppress `ShoppingTooltip1`/`ShoppingTooltip2` for items |
| Hiding tooltip | Always `GameTooltip_Hide()` (global function), never `GameTooltip:Hide()` |
| Click handler | Always include `PlaySound(SOUNDKIT.*)` |
| Movable frame | Always call `SetClampedToScreen(true)` |
| Combat-sensitive UI | Use `QR:RegisterCombatCallback(enterCb, leaveCb)` |
| Secure button needed | Use `SecureActionButtonTemplate`, anchor to UIParent, position via `QR.SecureButtons:AttachOverlay()` |
| Renaming with replace_all | Bulk replace catches declaration lines too — fix declarations after |
| Setting a waypoint during a route refresh | TomTom's `Waypoint` callback re-enters `UI:RefreshRoute()`. Keep the `isCalculating` guard, set the waypoint from `C_Timer.After(0, …)` and skip it when `routeGeneration` changed, and set `_settingWaypoint` around `TomTom:AddWaypoint` |
| Overlay on UIParent that follows another frame | `SetScale(target:GetEffectiveScale() / UIParent:GetEffectiveScale())`, then `SetPoint(…, UIParent, "BOTTOMLEFT", …)` with the target's `GetLeft`/`GetTop` values unchanged. Never divide those offsets by `GetEffectiveScale()` |
| Displaying a teleport or destination name | Localized name from `C_Spell.GetSpellInfo(id).name`, `GetItemInfo(id)` or `C_Map.GetMapInfo(mapID).name`; static data names only as fallback |
| `GetLocalized*` helper that takes an entry | Return `""` when `entry` or `entry.data` is nil |
| Registering events or callbacks | Guard with a flag (`WaypointIntegration.hooksRegistered`) so a second call registers nothing |

## Boundaries

### Always
- Run tests before deploying (`~/.local/bin/lua5.1 tests/run_tests.lua`)
- Guard against nil before WoW API calls
- Use `QR.Colors`, `QR.L`, `QR.PlayerInfo` (never hardcode)
- Check `InCombatLockdown()` before secure frame operations
- Validate `weight > 0` for graph edges (use epsilon 0.001 for same-zone)

### Ask First
- Changing load order in `.toc`
- Adding new SavedVariables fields
- Modifying graph/pathfinding algorithm
- Adding new slash commands

### Never
- Use Lua 5.2+ features (goto, bitwise, floor division)
- Call `SetPoint`/`SetParent` on SecureActionButtonTemplate to non-secure frames
- Use `table.insert(path, 1, x)` in hot paths (O(n^2))
- Share frame pool instances across modules
- Use raw `print()` instead of `QR:Debug()`/`QR:Print()`

## Codebase State

- **SavedVariables**: `QuickRouteDB` (DB_VERSION = 1)
- **Diagnostic trace** (`Modules/Diagnostics.lua`): setting `diagnosticTrace`, default off, a checkbox at the end of the settings panel. While on, every `QR:Log` line and structured entries go into `QuickRouteDB.trace`: window show/hide/toggle with a `reason` from each call site and a trimmed `debugstack`, waypoint triggers (event or TomTom callback, the tracking state, what was done with it; the waypoint itself is traced only where `_ProcessWaypointChange` resolves it, because resolving a quest at trigger time caches "not found" for it), quest/NPC/zone/travel events (registered only while on, each guarded by `pcall` because the two clients know different events; the ones that failed are listed in the session entry), taxi transitions, asynchronous route requests and results, Lua errors. A ring buffer of `TRACE_CAP` = 20000 entries and an estimated `TRACE_MAX_BYTES` = 6 MiB; QUEST_LOG_UPDATE and QUEST_POI_UPDATE are throttled to one entry per 2 s each, with the hidden count on the next. Measured with `tests/make_trace_fixture.lua retail OUT 20000`: entries the size of a real session reach the byte bound first, at 17,023 entries, and the SavedVariables file is then 5.4 MB (5,384,816 bytes; the estimate runs about 17% above the written size). `/qrdiag clear` deletes it. ZONE_CHANGED*, PLAYER_ENTERING_WORLD and both LOADING_SCREEN_* entries also carry the game map: `instanceName`, `instanceType`, `difficultyID` and `instanceMapID` from `GetInstanceInfo()`, `bestMap` and `bestMapType` from `C_Map`; the session entry carries the character's `race` (the file token from `UnitRace`), `raceID`, `faction`, `class` and `level`. What the trace cannot tell: WoW exposes no phase ID for the player. A phase or terrain swap that moves the player to another game map (Forever's 2980 "Dalaran City" or the instanced 2959 "City of Dalaran" instead of Eastern Kingdoms, 0) shows as a different `instanceMapID`; a phase on the same game map changes nothing the trace records, so it stays invisible. Window opens pass a reason: give a new call site of `MainFrame:Show/Hide/Toggle`, `UI:Show/Hide/Toggle` or `TeleportPanel:Show/Hide/Toggle` its own reason string. SavedVariables are written on `/reload` or logout only.
- **Auto-destination** (`autoDestination`, `WaypointIntegration:_ProcessWaypointChange`): a waypoint change opens the route window only when there is a waypoint and it lies in another zone than the player (`WaypointIntegration:IsInOtherZone`: both points resolved with `PathCalculator:ResolveMapPosition`, then a destination in a sub-zone of the player's zone, or the player in a sub-zone of the destination's, counts as the same zone; only a map routing cannot place (`PathCalculator:IsRoutableMap`) climbs to its UiMap parent, so Undermine stays apart from The Ringing Deeps; a continent map is no zone). When the player's map cannot be read, the window opens as before. An open route window is refreshed for every change. The trace records `auto-show`, `skip-same-zone`, `skip-cleared` or `skip-unresolved` (a quest is still super-tracked but has no coordinates yet) with `playerZone` and `destZone`; an unresolved quest is looked at once more on the next QUEST_POI_UPDATE (`WaypointIntegration:OnQuestPOIUpdate`), once per spell of tracking that quest; any other outcome of a later change spends the arming, so a quest resolved another way is not reopened by a stale retry. Tests drive the event through WaypointIntegration's own handler (`fireWired` in `tests/autoshow_cases.lua`, re-registering the hooks because `MockWoW:Reset()` drops handlers). The client changes super-tracking by itself on QUEST_ACCEPTED and QUEST_TURNED_IN, so without this the window opened in the quest giver's dialog.
- **Zone survey** (`Modules/ZoneSurvey.lua`): off unless the player switches it on, with the settings checkbox (after the diagnostic trace) or `/qrsurvey on|off`. Both go through `ZoneSurvey:SetEnabled`, which also sets `zoneSurveyChoice = true`; do not write `zoneSurveyEnabled` anywhere else. Releases v1.16.0 to v1.21.2 switched the survey on by themselves when the value was unset, so `ZoneSurvey:MigrateDefault` (run by `Initialize`) turns a stored `true` without `zoneSurveyChoice` off and prints `ZONE_SURVEY_NOW_OFF` once; the recorded `zoneSurvey` data stays. A test that loads the survey through `Initialize` with it on must set the marker too (`tests/test_zonesurvey.lua` does in `resetState`).
- **Travel observations** (`Modules/DataCollection.lua`): setting `dataCollection`, default off, its own settings checkbox after the zone survey's, and `/qrdata on|off|clear` (`/qrdata` alone prints the counts). Both go through `DataCollection:SetEnabled`, which drops a pending cast and a followed route when switched off and refreshes the save reminder; it does not touch the zone survey, which has its own switch. While on, six capped lists under `QuickRouteDB.observations`, exact repeats collapsed into a `count`: `landings` (a known teleport against the landing the data expects), `unknownTeleports` (a spell followed within 3 s by a loading screen; with both ends, the spell, the faction, the loading time and the game map from `GetInstanceInfo` on both sides, read through `Diagnostics.GameMapFields`, which is what an entry in `scripts/data/forever_observed_portals.json` needs), `noRoute`, `stepTimes`, `rejectedSteps`, `calcTimes`. Only the live `QR.PathCalculator` is recorded: a route context (the multi-stop planner's leg matrix) goes through the same `CalculatePath` from other starts and is skipped. Whether a followed route was abandoned is decided by the waypoint, never by the route window (MainFrame hides itself when combat starts, and travelling with it closed on TomTom's arrow is supported): timing is judged against what the panel would show on its next refresh (`UI:RefreshRoute`), at each waypoint signal and at each sample, told by WaypointIntegration directly so it works with the window closed. While `destinationLocked` is set and `lastDestination` is usable, the panel routes to `lastDestination`: a follow for that destination is kept, a follow for any other ends, at the next waypoint signal or the next sample (a map click or multi-stop leg chosen with the window closed only saves and locks). `OnWaypointCleared` (USER_WAYPOINT_UPDATED without a pin; in combat too, before the deferral) affects only a route to that pin (source `mappin`) or a `locked`/`map_click` route that is no longer locked; it never calls `GetActiveWaypoint`. `_ProcessWaypointChange` hands the resolved waypoint to `DataCollection:OnWaypointResolved`: the same destination keeps the route, another ends it, none ends it. Where a route would end but nothing is left to route to (no super-tracked quest, no map pin, no TomTom waypoint) and `lastDestination` is the followed destination, the panel falls back to it: the route goes on with its own source and `fallback = true` (recorded on the trip), and the next event is judged the same way again. Routes the panel showed as `saved`, and the `dungeon_offer` route, are never ended by a waypoint signal or a lock elsewhere, only by the panel or the time limit. The panel paths also end or replace a route: `UI:ClearRoute`, and `UI:UpdateRoute` with another destination or without steps. A trip taking more than 5 times its estimate (at least 300 s, at most 7200 s) is dropped. Known limit: QuickRoute's own TomTom step waypoints are not told apart from the player's in `GetTomTomWaypoint`, so with no quest or pin a TomTom arrival callback resolves to the next step and ends the route, as it would redirect the panel. `DataCollection:EndFollow` takes one last sample first, so an arrival since the last tick is still recorded; past the time limit the trip is dropped, not recorded. The route source comes from `result.waypointSource`. A cast of a spell the player knows (`IsPlayerSpell`) is still written to `unknownTeleports`, flagged `playerSpell`: the assumption, unconfirmed in the game, is that a portal object's click is not reported as a player spell, and the flag keeps such a click from being lost if it is. The eight events and the sampling `OnUpdate` are registered only while the switch is on (`DataCollection:ApplySetting`). Every recording runs inside `pcall`. `DataCollection.unsavedCount` counts writes, a collapsed repeat included, for the save reminder; `/qrdata clear` resets it. Not yet seen in the game: whether the Forever client fires `UNIT_SPELLCAST_SUCCEEDED` when a portal object is clicked. If it does not, a loading-screen crossing in the zone survey has no `unknownTeleports` entry beside it.
- **Save reminder** (`Diagnostics.Reminder`, same file): while the diagnostic trace, the zone survey or the travel observations are on and something was recorded since login or the last `/reload` (`Diagnostics.unsavedTrace`, `ZoneSurvey.unsavedCaptures`, `ZoneSurvey.unsavedCrossings`, `DataCollection.unsavedCount`), a small window (`QuickRouteSaveReminder`, `CreateStandardWindow`, ESC closes it) offers "Reload now" every `saveReminderMinutes` (default 20, 5-120) and closes itself after `saveReminderTimeout` seconds without the pointer on it (default 30, 10-120); `saveReminder` (default on) switches it off. The interval counts from login, the last reminder or its close. It is never shown in combat (`InCombatLockdown`, `UnitAffectingCombat`), on a taxi (also when `UnitOnTaxi` will not say), during a loading screen, in an instance, during an encounter or while `SecureButtons.pendingReleases` is not empty; a reminder due then waits for the next check (every 5 s, from an `OnUpdate` that only adds elapsed time), and for the end of combat, a loading screen or a taxi ride. It hides when combat starts and comes back after it. The reload button calls `C_UI.Reload`, else `ReloadUI`, and refuses in combat. The ticker frame is hidden (no `OnUpdate`) unless reminders apply; `Reminder:Refresh()` follows the trace, the survey, the observations and the reminder setting. The window's text is laid out as wrapping lines; `tests/reminder_cases.lua` checks under the mock's 7 px per byte that the Latin-script locales fit (the mock cannot measure Cyrillic, Hangul or Han, which take 2-3 bytes per character).
- **Interface**: `120105` (WoW 12.1.5). The live retail build is the authority — check https://wago.tools/api/builds, not the wiki, which lags.
- **WoW Forever**: `QuickRoute_Camelot.toc`, interface `16001` (product `wowf`, build 1.60.1.70862, client game type "camelot"). `QR.IsForever` is `WOW_PROJECT_ID == WOW_PROJECT_CAMELOT`; use it only where code must differ at runtime. Forever UiMap IDs are the Classic set (Stormwind 1453, Orgrimmar 1454), so a retail map ID in `Data/Forever/` is a bug — `tests/test_forever_data.lua` checks every one.
- **Release version**: a release bump sets `## Version:` in BOTH `QuickRoute/QuickRoute.toc` and `QuickRoute/QuickRoute_Camelot.toc` (plus the CHANGELOG section). `.github/workflows/release.yml` and `scripts/hooks/pre-push` reject a tag that does not match either TOC, and `tests/test_flavor_tocs.lua` fails when the two TOCs' metadata differ.
- **Dependencies**: none required. TomTom optional (`## OptionalDeps`). No libraries are vendored and there is no `embeds.xml`.
- **CI**: GitHub Actions — luacheck 1.2.0 over `QuickRoute/` and `tests/`, plus the full Lua 5.1 test suite, on push/PR to main. Actions are SHA-pinned and maintained by Dependabot. The `Dependabot auto-merge` job in `ci.yml` merges a Dependabot patch or minor update with a merge commit once every check on its head commit passed; majors stay open for a human. A merge made by that job raises no push event, so main gets no CI run for it.
- **Shipped since the last VISION revision**: dungeon/raid routing, destination search, service-POI routing, Encounter Journal button, multi-stop trips, the public routing contract (`QuickRouteAPI`), journey ownership, target roles, coordinate provenance, refusing a step, and the hearthstone inn catalogue.
- **Planned features**: NPC/vendor routing, world events (see `docs/VISION.md`)
